## 0. 基线：先确认要优化的到底是什么

| 项目 | 结果 |
| --- | --- |
| 构建一致性 | `node _build/build.mjs --check` → **一致**（29 模块 / 5663 行） |
| 测试 | **9 个套件 / 519 项全部通过**（原 8 套件 444 项）（`engine` / `browser-ai` / `web-translate` / `opt` / `allsite` / `smoke-panel` / `layout` / `fullscreen`） |
| 体积 | 286.5 KB / 5664 行 |

**关键判断：JS 层微优化的边际收益已经很低。**

依据是仓库自己的记录：v1.7.0 → v1.12.0 之间已经做过 **8 轮热路径优化**，覆盖了
画布复用、类型化数组 scratch、滚动行缓冲、强制重排消除、存储精确写入、
遍历去分配。`docs/ARCHITECTURE.md:583` 也已给出结论：

> 真正的成本在网络与图像编解码，因此优化重点放在「减少浪费」（跳过判定、缓存）
> 与「消除每帧的分配」上，而不是微调 JS 循环。

因此本方案**不提议继续压榨 JS 循环**，而是把重心放在三个尚未被系统处理的方向：

1. **浪费掉的钱** —— 有若干条路径会在「画面完全没变」时持续调用付费接口；
2. **时延** —— 固定 1200ms 轮询是响应速度的硬地板；
3. **验证基建** —— 444 项断言目前**没有任何自动化执行入口**。

### 补充：一次独立性能审计的结论（已并入下文）

对热路径做了一次逐行审计 + 仓库自带基准数据（`_test/_bench-last.json`）核对，
结论与上面一致，并给出了具体量级：

| 项目 | 实测单次成本 |
| --- | --- |
| `Capturer.grab` | 0.43 ms |
| `canvas.toDataURL(jpeg)` | 0.64 ms |
| `edgeDensity` | 0.08 ms |
| `thumbnail` | 0.013 ms |
| `Overlay.show` + 定位 | 0.056 ms |
| 300 轮热路径堆增长 | **0 KB** |

一轮完整调用合计约 **0.6–1.3 ms**，而周期 ≥1200 ms —— 占空比 **< 0.1%**。
**这从数量上证实了「不要再去抠 JS 循环」这个判断。**

另有两个重要的结构性事实：

1. **真实请求周期不是 `CFG.interval`。** `tick()` 是在 `step()` 结算**之后**才排下一次
   定时（`src/70-pipeline.js:79-81`），所以
   `周期 = interval + 分析耗时 + 完整 API 往返`。1.2s 间隔 + 1.5s 视觉模型延迟
   ≈ 每 2.7 秒一次调用。**这对省钱是好事、对实时性是坏事** —— 想「修」它就会增加花费，
   所以 P1-1 必须与节流策略一起设计，不能单独提速。
2. **两个真实缺陷被交叉确认**（已补为 P2-1b / P2-1c）：`stop()` 不清 `busy` 导致
   重启被静默吞掉；相似句判重发生在付费调用**之后**。

## 1. P0：省钱与正确性（性价比最高，建议优先）

### P0-1 「识别不出文字」时，同一帧会被无限重复送去付费识别

**问题**
`shouldSkipFrame()` 的「画面未变化」跳过带了一个 `this.lastOriginal` 前提：

```js
// src/70-pipeline.js:181-189
const noChange = this.lastThumb && thumbDiff(thumb, this.lastThumb) < NO_CHANGE_DIFF;
if (noChange && this.lastOriginal) {          // ← 前提在这里
    this.stats.skipped++;
    UI.setStatus('画面未变化，跳过', 'idle');
    return true;
}
this.lastThumb = thumb;
```

而 `present()` 在识别结果为空时会把 `lastOriginal` 清成空串：

```js
// src/70-pipeline.js:264-273
if (!res.original && !res.translation) {
    this.emptyStreak++;
    if (this.emptyStreak >= 2) {
        Overlay.clear();
        this.lastOriginal = '';               // ← 清空后，上面的跳过永久失效
    }
```

**后果**：只要出现「画面静止 + 边缘密度够高（不会被 `smartSkip` 拦下）+ 识别不出文字」
的组合，`lastOriginal` 就一直是空串，`noChange` 的短路条件永远不成立 →
**每隔一个截图间隔就重新识别一张逐像素相同的图**。API 每次都会返回同样的空结果，
用户什么都看不到，但钱照扣。

典型触发场景：静止的空镜 / 风景镜头、纯纹理背景、静止的标题卡、画面里有高对比度
背景但没有字幕的时段。这不是理论边界——它是「静止且无字幕」这段时长除以 1.2 秒。

**改法**：把「跳过」的判据从「上一帧识别到了文字」改成「上一帧这个画面已经处理过」。
即记录 *上次实际发起识别时的缩略图*，只要当前帧与它相同就直接跳过，无论当时
识别结果是否为空：

```
this.lastThumb      // 语义：上次「看过」的帧（现状）
this.lastSentThumb  // 新增语义：上次「送出去识别过」的帧
```

判据变为 `noChange && lastSentThumb` —— 与识别结果解耦。`present()` 里的
`emptyStreak` 逻辑保持不动（它负责的是「悬浮层何时收起」，是另一件事）。

**收益**：高。直接消除一整类无效付费调用，且完全符合设计目标 3「省钱」。
**风险**：低。唯一的行为变化是「静止且无字幕」的时段不再重复识别——而那本来就
不会产生任何可见输出。需要在 `_test/opt.mjs` 补一条断言：**静帧 + 空结果连续
N 轮，`stats.apiCalls` 只增加 1**。

### P0-2 后台标签页里仍在截图并调用付费接口

**问题**
全仓库检索 `document.hidden` / `visibilitychange`：**零命中**（`src/` 下无任何实现）。
`Pipeline.tick()` 用的是 `setTimeout`，后台标签页只会被节流到约 1 秒，**不会停止**。
而视频在后台标签页是继续播放的，所以脚本会继续截图、继续调 API。

**后果**：用户切到别的标签页/最小化窗口去看别的东西时，字幕翻译仍在全速烧钱，
而且没有任何人看得到结果。注意**只播放音频时 `video.paused` 仍为 `false`**，
所以现有的「视频暂停就不截图」这道闸门（`src/70-pipeline.js:124`）**拦不住**这种情况。

**改法**：监听 `visibilitychange`，隐藏时暂停主循环，可见时恢复（并作废在飞结果）：

```js
document.addEventListener('visibilitychange', () => {
    if (document.hidden) Pipeline.pauseForHidden();   // 停表 + invalidate，不动 CFG
    else Pipeline.resumeFromHidden();
});
```

要点：
- 必须是「暂停/恢复」而不是 `stop()` —— `stop()` 会 `Overlay.clear()` 并重置
  `lastOriginal`，用户切回来会看到字幕消失且重新开始（`src/70-pipeline.js:44-56`）。
- 恢复时 `invalidate()`，避免切走期间飞在路上的结果回来画到画面上。
- 默认行为建议做成可配置（`pauseWhenHidden`，默认 `true`），并在状态栏给出
  「已切到后台，暂停中」的提示 —— 与「失败要说话」这条设计主线一致。

**收益**：高（这是最容易发生、也最纯粹的浪费）。
**风险**：低。唯一需要留意的是**纯音频**场景（听剧），但那本来也不该开字幕翻译。

### P0-3 限流（429）没有退避，会被持续敲打
**问题**
两处：

```js
// src/70-pipeline.js:74-76  —— 出错后固定睡 1500ms
UI.setStatus('出错：' + e.message, 'err');
await sleep(1500);          // 固定值，不区分错误类型
```

```js
// src/60-chat.js:116  —— 429 只变成一句提示文案
else if (r.status === 429) msg += '　→ 请求太频繁或额度用尽，试试调大截图间隔';
```

全仓库检索 `retry` / `backoff`：**没有任何重试或退避实现**。

**后果**：撞上限流后，脚本以约 2.7 秒的周期继续请求，`stats.errors` 一路涨、
状态栏一直红，服务端的限流窗口被反复续期 —— 恢复时间反而被拉长。

**改法**：在 `Pipeline` 引入按错误类型区分的退避：

| 错误 | 退避策略 |
| --- | --- |
| 429 / 402 / 401 | 指数退避，1s → 2s → 4s → … 封顶 60s；状态栏显示「已退避 Ns」 |
| 5xx / 网络错误 / 超时 | 指数退避，1s → 2s → 4s，封顶 15s |
| 4xx（模型名、地址写错） | **不退避**，直接停并提示用户改配置（重试没有意义） |

实现上建议在 `tick()` 的成功/失败分支里维护 `this.backoff`，成功后清零。
`docs/ARCHITECTURE.md:317` 已有「错误处理与退避」小节，本次是把它**真正实现**。

**收益**：中高（减少无效请求、缩短限流恢复时间、状态栏不再刷屏）。
**风险**：低。需要一条断言：连续 3 次 429 后，第 4 次请求的间隔 ≥ 前一次的 2 倍。

## 2. P1：时延与响应速度

### P1-1 用 `requestVideoFrameCallback` 取代「固定间隔轮询」作为默认采样源

**问题**
`CFG.interval` 默认 1200ms（`src/10-config.js:76`），这是**探测新字幕的延迟地板**。
一句字幕出现后，平均要等 600ms 才可能被截到，最坏 1200ms；再叠上 API 往返，
用户体感延迟普遍在 1.5 秒以上。而字幕本身往往只显示 1~2 秒。

**改法**：新增「自适应采样」模式（`interval` 保留为回退）：

- 视频播放时用 `video.requestVideoFrameCallback()` 逐帧拿到「有新画面」的通知；
- 在回调里跑**现有的** `thumbnail` + `thumbDiff`（512 像素，成本已降到很低），
  只在画面真的变化时才进入后续的 `edgeDensity` → 识别；
- 仍受 `this.busy` 与一个最小间隔（如 200ms）约束，确保同一时刻只有一个请求在飞；
- 不支持 `requestVideoFrameCallback` 的环境（旧 Firefox）自动回退到现有 `setInterval`。

**收益**：高。把探测延迟从「最多 1200ms」降到「一帧 + 节流」，同时因为
只在真实新帧上做判断，**无效判断次数反而下降**。这是本项目核心体验（实时性）
上剩余空间最大的一项。
**风险**：中。属于架构级改动，必须做成**可选模式**、默认保持现行为，并复用
`bench-ab.mjs` 给出前后对比（`_test/bench.mjs` 已有 `Pipeline.step·空转`
与 `thumbnail` / `edgeDensity` 三项基准，足以量化）。

### P1-2 识别结果按「图像指纹」缓存（覆盖 `openai-vision`）

**问题**
翻译缓存只服务**纯文本**路径：

```js
// src/62-engines.js:50-57  translateText() —— umi-ocr / browser-ai / web-translate 会走
const hit = cacheGet(text);
if (hit !== undefined) return hit;
```

而**默认引擎** `openai-vision` 完全不经过缓存：

```js
// src/62-engines.js:94
return await translateByVision(canvasToJpeg(canvas, 0.85));
```

**后果**：重复出现的同一句字幕（口头禅、片头、下集预告、暂停后重播同一段）
每次都要重新走一次视觉大模型。

**改法**：以 `thumbnail()` 产出的 32×16 灰度图为键，缓存
`{original, translation}`。命中条件要比 `thumbDiff` 更严格（例如平均差
< 0.001 且最大单点差 < 8），命中后**仍要过一遍** `present()` 里的文本相似度判断。

**⚠️ 风险与取舍**：32×16 量化存在**碰撞**可能 —— 两帧不同字幕缩略图接近时，
会显示上一句的译文。这与项目「不锚定是静默出错」的洁癖直接冲突。
建议：**先只做「相同键精确命中」+ 更强的指纹（64×32）**，并用
`_test/opt.mjs` 造几组「不同字幕但画面相似」的样本，确认不误命中；
若碰撞无法压到可接受范围，宁可放弃此项，保留 P0-1 的收益即可。

**收益**：中。**风险**：中（正确性风险，需要证据才落地）。**建议排在 P0 之后单独评估。**

### P1-3 点「停止」时取消飞在路上的请求

**问题**
`gmRequest` 没有暴露 `abort`：

```js
// src/40-http.js:7-21
function gmRequest(opts) {
    return new Promise((resolve, reject) => {
        GM_xmlhttpRequest({ /* … */ onload, onerror, ontimeout });
    });
}
```

用户点停止后，`gen` 校验会**丢弃结果**（`src/70-pipeline.js:226-229`，这部分是对的），
但请求本身仍在服务端继续生成 —— `maxTokens` 默认 1024，被丢弃的那部分照样计费。

**改法**：让 `gmRequest` 返回 `{promise, abort}`（或给 `opts` 传 `signal`），
`Pipeline.stop()` / `invalidate()` 时中断在飞请求。`GM_xmlhttpRequest` 本身返回一个
带 `abort()` 的对象，改动很小。

**收益**：中（尤其在长回复或慢模型上）。**风险**：低。需断言「停止后
`abort` 被调用且不产生 unhandled rejection」。

## 3. P2：健壮性（真实缺陷，但触发面较窄）

### P2-1 `browser-ai` + 端侧读图：画布快照的时机反了

**这是本次审计中唯一一处「代码自己在注释里写明了意图、实现却没做到」的地方。**

```js
// src/48-browser-ai.js:726-727（注释明确说明了为什么要转 blob）
/** 画布 → Blob。转一手是为了**快照**：captureMode 下画布是复用的，直接把 canvas 交给异步的
 *  模型调用，像素可能已经被下一帧盖掉。 */
function baiCanvasBlob(canvas) { /* canvas.toBlob(...) */ }

// src/48-browser-ai.js:759-761（实际顺序）
async function baiOcrByBuiltin(canvas) {
    const session = await baiOcrSession();     // ← 先 await（首次可能触发模型下载，数秒）
    const blob = await baiCanvasBlob(canvas);  // ← 快照发生在这里，已经晚了
```

`Capturer._out` 是**复用画布**（`src/50-capturer.js:17-18`、注释见 `:131`）。而在
`await baiOcrSession()` 让出事件循环期间，有两条路径会改写同一张画布：

- `UI.manualShot()`（`src/96-panel-ui.js:1240-1244`）**不检查 `Pipeline.busy`**；
- `RegionSelector.previewDrag()`（`src/86-selector.js:86`）在拖拽时按帧截图。

**后果**：识别到的可能是被覆盖后的**错误画面** —— 正是本项目最忌讳的「静默出错」。
好消息是另外四条引擎路径都是安全的：`canvasToJpeg()` 是同步调用，在首次 `await`
之前就完成了编码（`src/62-engines.js:82-94`）。

**改法**：把顺序倒过来 —— 先取快照，再等会话：

```js
const blob = await baiCanvasBlob(canvas);   // 先把像素钉住
const session = await baiOcrSession();
```

一行调序，语义立即与注释一致。

**收益**：中（修掉一类偶发错帧）。**风险**：极低。断言建议：让 `baiOcrSession()`
故意延迟，期间改写画布，验证最终识别用的是**改写前**的像素。

### P2-1b `stop()` 不清 `busy`：停止后 45 秒内点「开始」会被静默忽略

**问题**
`busy` 只在 `recognize()` 里被置位和清除：

```js
// src/70-pipeline.js
213: this.busy = true;
221: this.busy = false;      // finally 里
```

`stop()`（`:44-56`）与 `start()`（`:29-42`）**都不碰它**。而 `ensureReady()` 会因此
一直返回 false：

```js
// src/70-pipeline.js:130
if (this.busy) return false;     // ← 在飞请求结算前，重启被无声吞掉
```

`gmRequest` 的默认超时是 **45 秒**（`src/40-http.js:14`，`src/60-chat.js:102` 未覆盖）。
所以「点停止 → 立刻点开始」这个很自然的操作，在旧请求回来之前**完全没反应**：
状态栏显示「运行中…」，但一轮都不会跑。

**改法**：`stop()` 里清掉 `busy`（配合已有的 `gen` 校验，迟到的结果本来就已被丢弃），
或让 `start()` 无视旧的 `busy`。若要连钱一起省，见 P1-3 的请求取消。

**收益**：中（修掉一个只有读代码才能发现的 UX 缺陷）。**风险**：低 ——
`gen` 机制已经保证迟到结果不会被画上去，清 `busy` 不会引入过期字幕。

### P2-1c 「先付钱、再丢弃」：相似句的判重发生在调用之后

**问题**
`shouldSkipFrame()` 只比较**像素**；真正的「这句和上句是同一句」判断发生在
`present()` 里，而那时钱已经花了：

```
step()  → recognize()   ← 这里的 await 已经把请求发出去了（计入费用）
        → present()     → textSimilarity 判定「与上句相似」→ 丢弃结果
```

只要像素变化超过 `NO_CHANGE_DIFF = 0.004`（这个阈值**极低**，`src/14-constants.js:14`）
而字幕文本没变 —— 比如字幕背后有运动画面、胶片颗粒、编码噪声 —— **每一轮都会买一次
视觉模型调用，然后把答案扔掉**。

**改法**：把「被判为相似」的那一帧的缩略图指纹记下来，下次遇到相同指纹直接短路
（需要把 thumb 传进 `recognize`）。因为那些结果本来就被丢弃，**可见输出完全不变**。

**⚠️ 前置条件**：`stats.skipped` 目前**不区分跳过原因**，所以无法知道这条路在真实
使用中到底浪费了多少。建议**先加一个按原因分开的计数**（一行的事），确认这个洞
确实在漏钱，再动手 —— 否则可能是在优化一个罕见分支。

**收益**：中（若确实高频，则是持续的小额漏钱）。**风险**：低-中（指纹量化不能
吞掉真实的字幕变化）。

### P2-2 `display` 模式有可能在「安静地截错区域」

`grabFromDisplay()` 用 `window.innerWidth/innerHeight` 作为坐标基准：

// src/50-capturer.js:160-168
const scaleX = (s.width || v.videoWidth) / window.innerWidth;
const scaleY = (s.height || v.videoHeight) / window.innerHeight;

截到无关像素、OCR 出一堆乱字、照常扣钱 —— 且不报错。

**收益**：中（把一类静默失败变成可见提示）。**风险**：极低。

### P2-4 「校验放宽了、消费端没跟上」：`hexToRgb` 不支持 3/4/5/8 位色值
**这是 P2-3 的镜像问题** —— 校验层接受、消费层解析不了，且失败方式是**静默**的。

`sanitizeCfg()` 的颜色校验正则允许 3~8 位十六进制：

```js
// src/10-config.js:170-172
if (typeof cfg.textColor !== 'string' || !/^#[0-9a-fA-F]{3,8}$/.test(cfg.textColor)) {
    cfg.textColor = DEFAULTS.textColor;
}
```

但 `hexToRgb()` 只认**恰好 6 位**，其余一律回退成白色：

```js
// src/84-html.js:53-58
function hexToRgb(hex) {
    const m = /^#?([0-9a-f]{6})$/i.exec(String(hex || '').trim());
    if (!m) return [255, 255, 255];      // ← 静默当成白色
    …
}
```

实测（Node 复现两条正则）：

| 输入 | `sanitizeCfg` 通过？ | `hexToRgb` 结果 | 后果 |
| --- | --- | --- | --- |
| `#ff0000` | ✅ | `[255,0,0]` | 正常 |
| `#f00` | ✅ | `[255,255,255]` | **静默变白** |
| `#ff000080` | ✅ | `[255,255,255]` | **静默变白** |
| `#abcde` | ✅ | `[255,255,255]` | **静默变白** |

`docs/ARCHITECTURE.md:631` 的文档明确写着白名单是「`#RGB`~`#RRGGBBAA`」，
所以**文档、校验、消费端三者不一致**。

**实际触发面（诚实评估：窄）**
- 面板上的 `type="color"` 控件（`src/90-panel-html.js:236`）**永远只产出 `#rrggbb`**，
  正常操作路径碰不到；
- 但**导入配置**、以及手工写 `GM_setValue` 可以带入这些值 —— 而
  `sanitizeCfg` 会**放行**它们（导入路径确实会调它，`src/96-panel-ui.js:771` 附近）；
- 后果是「用户设了个颜色 → 显示成白色」，与项目「不静默出错」的洁癖冲突。

**改法（二选一，推荐前者）**：任选一种让三者一致。
1. **扩 `hexToRgb`**（改动小、更符合文档）：补上 `#RGB`/`#RGBA` 短式展开，
   8 位取前 6 位（或把 alpha 也返回，供 `Overlay.applyStyle` 用）；
2. **收紧校验**：正则改为 `^#([0-9a-fA-F]{3}|[0-9a-fA-F]{6})$`，并同步改
   `ARCHITECTURE.md:631` 与 README 的说明。

**风险**：低。若选 2，需确认没有已发布配置依赖 8 位色值（老配置里的非法值会被
兜回默认白，行为可接受）。断言建议：`#f00` → `[255,0,0]`，且 `#ff000080` 不再变白。

### P2-5 跨管理器：`window.__H1SUB__` 调试钩子在隔离沙箱里取不到（**未完全验证**）

`@grant` 列表（`src/00-header.js:13-16`）里有 4 个 `GM_*`，**没有任何 `@grant none`
或 `@sandbox` 指令**。在 Tampermonkey 下 `window` 通常就是页面窗口，所以钩子可用；
但**在 Violentmonkey / Greasemonkey 的隔离沙箱下，脚本里的 `window` 可能是沙箱的
`window` 而不是页面的** —— 那么 `window.__H1SUB__` 在页面控制台里取不到。

**影响面**：只影响**调试与文档**，不影响翻译主流程（主流程不用这个钩子）。
`docs/API.md:452-461` 明确教用户「在控制台里 `const H = window.__H1SUB__`」，
`README.md:9` 的徽章也把 Violentmonkey 列为支持平台。

**⚠️ 我必须标明不确定性**：审计这条的那个子代理**耗尽上下文、没有产出报告**，
所以这一条是**我自己的阅读推断，未经实测**。三个管理器对 `window` 的处理差异
我**没有在真实环境里验证过**。

**建议**：若要处理，最小改动是把赋值补上页面窗口兜底
（`(typeof unsafeWindow !== 'undefined' ? unsafeWindow : window).__H1SUB__ = …`），
但那需要新增 `@grant unsafeWindow`，会改变权限提示。
**更稳妥的做法是先实测**：分别在 Tampermonkey 与 Violentmonkey 里加载产物，
在页面控制台敲 `window.__H1SUB__` 看是否 `undefined`。
**在拿到实测结果前，不建议动这一块。**

## 4. P3：结构、可维护性与验证基建

### P3-1 加 CI —— 目前 444 项断言没有任何自动化执行入口

`.github/` 下只有 `PULL_REQUEST_TEMPLATE.md` 与 `ISSUE_TEMPLATE/`，
**没有 `workflows/` 目录**。`CONTRIBUTING.md:394` 要求「确认 main 上全部测试通过」，
`README.md` 与 PR 模板也都把「444 项全过」写成硬门槛 —— 但这件事**完全依赖人工自觉**。

**改法**：新增 `.github/workflows/ci.yml`，在 push / PR 上跑：

```
node _build/build.mjs --check   # 产物与 src/ 一致（拦住「改了 src 忘了构建」）
node --check video-hardsub-translator.user.js
npm test                        # 8 个套件
```

`docs/TESTING.md:455-480` **已经写好一份可直接粘贴的 YAML**，照抄即可。

**⚠️ 一个必须知道的工作流陷阱**：`package.json:34` 的 `"pretest": "npm run build"`
意味着 **`npm test` 会先重新生成产物** —— 所以「改了 `src/` 却忘了构建」这种漂移
**永远不会让测试失败**。只有单独跑 `build:check` 才能发现。而 `build:check`
既不在 `test` 链里、又没有 CI —— 只跑 `npm test` 的贡献者会得到**虚假的完成感**。

因此 CI 至少要**分两个 job**：
- `build`：`build.mjs --check` + `node --check` —— **只依赖 Node，零 flake，今天就能上**；
- `test`：8 个套件 —— 需要 Chrome，建议先只跑 `windows-latest` 与作者环境对齐
  （`docs/TESTING.md:453` 已诚实说明本仓库从未在 CI 上跑过，且各套件**固定端口**、
  必须串行执行；Linux 从未验证）。

**收益**：高（把三条硬性规则从「文档约定」变成「机器强制」）。**成本**：低。
**这是整份方案里性价比最高的一项。**

### P3-2 给 `_build/build.mjs` 补测试 —— 它是唯一零覆盖的关键组件

`build.mjs` 守卫了 7 条规则（模块编号重复、依赖提供者存在、跨模块重名、
三处版本号一致、CR、语法门、`--check` 漂移），但**没有任何测试引用过它**

**后果**：没有任何证据表明这些守卫在**被违反时真的会失败** —— 而它们防的恰恰是
「静默作用域覆盖」这类最难排查的问题。守卫本身失效了也没人知道。

**改法**：新增 `_test/build.mjs`，把 `src/` 复制到临时目录，**每次只改坏一样东西**，
断言退出码非 0 且报错信息符合预期：

| --- | --- |

| `package.json` 改版本但 `@version` 没改 | 非 0 + 版本不一致提示 |
| 产物末尾追加一个字节后跑 `--check` | 非 0 + 漂移提示 |

**收益**：中高（补上基础设施最大的测试盲区）。**成本**：中（S/M）。

**顺带两条已证实的小隐患**：

### P3-4 给构建脚本加一条「依赖声明未被使用」检查

`_build/build.mjs` 已经校验了：模块命名与编号、声称提供的名字是否真的定义、
依赖的名字是否有人提供、顶层名字唯一、三处版本号一致。

**仍缺一条**：模块头「依赖」里声明了、但代码里**从未使用**的名字。这类漂移目前
只能靠人工审查发现，而它恰好会让模块地图（`docs/ARCHITECTURE.md` 的模块表）慢慢失真。

**这不是理论问题 —— 漂移已经发生了。** 一次交叉核对的结果：

| 模块 | 未声明的跨模块引用 |
| --- | --- |
| `98-boot.js` | **80 个**（根因：`:9-13` 只声明 20 个依赖，但 `:78-111` 的 `window.__H1SUB__` 对象字面量重导出了约 80 个标识符，模块头从未同步） |
| `96-panel-ui.js` | 3 个（`uiHost`、`wtReset`、`warn`） |
| `70-pipeline.js` | 2 个（`EDGE_MIN`、`NO_CHANGE_DIFF`） |
| `30-image.js` | 反向问题：声明了 `EDGE_MIN`，但代码里从未引用（陈旧声明） |

**改法**：在 `build.mjs` 里对每个模块做一次词法级扫描（顶层名字是已知集合，
不需要 AST），「声明了但没用」与「用了但没声明」两个方向都报出来。
**零依赖，符合现有构建哲学。**

**⚠️ 落地建议：先只报 warning。** 因为 `98-boot.js` 的 `window.__H1SUB__` 钩子
（`:78-111`，约 34 行）从**每个模块**重导出了约 80 个名字，而它的模块头（`:10-13`）
只声明了 20 个 —— 直接开成 error 会让构建立刻失败。这个钩子是**刻意的调试/测试接口**
（`docs/API.md:452-461`），也是测试能跑起来的前提，所以正确处理是
「先 warning → 把声明补齐 → 再转 error」。

**最有力的一条证据**：`30-image.js:11` 声明依赖 `EDGE_MIN`，但该文件里
**从未引用它**；真正的使用者是 `70-pipeline.js:197`，而那个文件**没有声明**。
**声明写在了错误的文件上，构建完全看不出来** —— 因为 `14-constants.js` 确实
提供了这个名字，单向检查就满足了。同理 `NO_CHANGE_DIFF` 用在 `70-pipeline.js:182`
也没被声明。

**另需说明**：`ARCHITECTURE.md:104` 与 `README.md:786` 写的「后文可以依赖前文」
实际上**有 22 条反向边**（如 `22-site.js`(idx 5) 依赖 `96-panel-ui.js`(idx 27) 的 `UI`；
`44-umi-ocr.js`(11) 依赖 `62-engines.js`(17) 的 `translateText` —— **适配器依赖调度器**）。
今天不出问题，是因为所有跨模块调用都在**函数体内**（拼接期不触发提升/TDZ）——
全仓库只有 2 条顶层语句，都在 `98-boot.js:152-153`。
也就是说「编号即顺序」这条规则对那 22 条边是装饰性的，`build.mjs` 也不检查顺序。
**建议在文档里把这个真实约束写清楚：「跨模块调用必须发生在函数体内」才是真正的规则。**

### P3-5 封装在 8 处漏水：同一对重置被执行了 4 遍

```js
Pipeline.lastThumb = null;
Pipeline.lastOriginal = '';
```

这两行被**手工复制了 4 份**：`src/96-panel-ui.js:413-414`、`:420`、
`src/86-selector.js:131-132`、`src/98-boot.js:144-145`。

根因是 `Pipeline.invalidate()`（`src/70-pipeline.js:27`）只 `gen++`，
**不重置这两项**，于是每个调用方都得自己补上剩余部分。这既是封装缺陷，
也是**潜在的逻辑隐患**：将来再加一个调用方，很容易只 bump `gen` 而忘了重置，
表现为「换了配置后第一句字幕被当成重复句吞掉」。

**改法**：把这对重置收进 `Pipeline`（例如 `Pipeline.resetFrameState()`，
或让 `invalidate()` 直接负责），4 处调用点改为一次调用。

**收益**：中（消除 4 份重复，堵住一类未来 bug）。**风险**：低。

### P3-8 `pushHistory` 每句都新建 DOM

## 7. 一条被实测否掉的提议：`baiCanvasBlob` 的 JPEG 质量「过高」

**提议**：`src/48-browser-ai.js:740` 用 `toBlob(..., 'image/jpeg', 0.9)`，同项目其它路径
是 0.85~0.92，所以 0.9「过高」，应该调低。

**结论：这条不成立。** 理由有两条，第一条是决定性的。

### 7.1 这条路根本不上传网络

`baiOcrByBuiltin` 产出的 blob 只喂给**浏览器内置的端侧模型**
（`src/48-browser-ai.js:759-776` 的 `session.prompt([...{ type: 'image', value: blob }])`）。
它**不经过 `gmRequest`、不出设备、不按字节计费**。

对照同文件 `:785`：Umi-OCR 那条路用的才是 `canvasToJpeg(canvas, 0.92)` —— 而
Umi-OCR 的默认地址是 `http://127.0.0.1:1224`（`src/10-config.js:51`），**是本机回环**。

也就是说，0.9 / 0.92 这两处「高」质量值，**没有一处会因此多花钱**。
它们的代价只是本地编码耗时（实测 1.6~2.1 ms）与内存里的 blob 大小。
真正上传到**付费云端**的是 `translateByVision` 的 **0.85**（`src/62-engines.js:94`）——
而它恰恰是全项目**最低**的一档。

**所以「质量值偏高」这个观察，指的全是免费路径。**

### 7.2 就算想调低，也换不到什么

在无头 Chrome 153 里实测（`node _jpeg_probe.mjs`，深色噪点背景 + 带描边白字，
即典型的硬字幕画面）：

| quality | 1400×116 体积 | 相对 q0.9 | 800×200 体积 | 相对 q0.9 |
| --- | --- | --- | --- | --- |
| 0.6 | 41.2 KB | −51.7% | 36.7 KB | −52.0% |
| 0.75 | 55.6 KB | −34.6% | 49.8 KB | −34.9% |
| 0.85 | 72.0 KB | −15.5% | 64.5 KB | −15.6% |
| **0.9** | **85.1 KB** | — | **76.4 KB** | — |
| 0.92 | 91.2 KB | +7.1% | 81.8 KB | +7.1% |
| 1.0 | 251.5 KB | +195.4% | 226.3 KB | +196.1% |

- **0.9 → 0.85 只省 15%**，代价是压缩伪影增加，而端侧模型读图对字形边缘敏感；
- 真正省得多的是 0.6（省一半），但那已经进入明显损伤字形的区间；
- 反向也值得记一笔：**`1.0` 会让体积膨胀到 3 倍**（JPEG 在高频噪点上几乎不压缩），
  所以如果哪里误用了 `1.0` 才值得报警 —— 而现有代码没有这样做。

### 7.3 结论与建议

- **不要为「省钱」调低端侧路径的 0.9 / Umi-OCR 路径的 0.92** —— 它们不花钱；
- 0.9 这个值处在体积曲线**拐点之后**：从 0.9 再往上，体积快速上涨而几乎换不到质量
  （0.92 +7%、0.95 +27%、1.0 +195%）；往下调则直接损失边缘锐度。
  **它是个合理的经验取值，不是「过高」。**
- 唯一值得考虑的相关改动是**可配置化**：把上传到云端那一路（当前硬编码 0.85 与
  1~3× 放大倍率）暴露成设置项。这与独立审计的 P2「把预上传放大倍率做成可配置」一致 ——
  但那是**质量/费用的权衡开关**，默认值应当保持现状。

> 说明：`_jpeg_probe.mjs` 是我为验证这条提议写的一次性测量脚本（含两种代表性尺寸、
> 9 档质量），未纳入测试套件。若要保留证据，建议按 `CONTRIBUTING.md` 的
> `bench-ab.mjs` 流程固化，而不是留在根目录。
