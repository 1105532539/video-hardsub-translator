# 本地 OCR 方案设计文档

> 目标:让「网页视频硬字幕实时翻译」脚本在**不联网下载大模型**的前提下做本地 OCR,
> 或在必须下载时把体积和集成成本降到最低。

---

## 一、先说约束

调研了 GitHub 上的浏览器端 OCR 方案后,有一个绕不开的事实:

**所有真正的 OCR 都需要模型权重。** 权重是几 MB 到几十 MB 的二进制,不可能内联进用户脚本。
所谓"零下载"只有一条路 —— **不用神经网络**。

所以下面的方案 C 才是真正意义上的"零下载",方案 B 是"用更大的下载换更高的准确率"。

---

## 二、方案 C:字符模板自学习(零下载)

### 2.1 原理

硬字幕有一个可以利用的强特性:

> **同一部片子里,字体、字号、描边风格完全一致,位置固定。**

这意味着:**同一个字在不同帧渲染出来的像素几乎完全相同。**

所以不需要"认识"这个字。只需要:

1. 把长得一样的字**归成一类**
2. 每一类**问一次**视觉大模型"这是什么字"
3. 之后遇到同类的字,**直接查表**,不再调 API

神经网络 OCR 是"每个字都要重新推理";这个方案是"每个字只需要认识一次"。

### 2.3 关键算法

#### (a) 二值化

字幕通常两种形态:

| 形态 | 特征 | 处理 |
|---|---|---|
| 白字黑边 | 字芯很亮、边缘很暗 | 取高阈值提字芯 |
| 黑字色带 | 字在纯色横条上 | Otsu 自动分 |

用 **Otsu 大津法**自动求阈值,无需配置:

```js
function otsu(gray) {
    const hist = new Uint32Array(256);
    for (let i = 0; i < gray.length; i++) hist[gray[i]]++;
    const total = gray.length;
    let sum = 0;
    for (let i = 0; i < 256; i++) sum += i * hist[i];
    let sumB = 0, wB = 0, best = 0, thr = 128;
    for (let t = 0; t < 256; t++) {
        wB += hist[t];
        if (!wB) continue;
        const wF = total - wB;
        if (!wF) break;
        sumB += t * hist[t];
        const mB = sumB / wB, mF = (sum - sumB) / wF;
        const between = wB * wF * (mB - mF) * (mB - mF);
        if (between > best) { best = between; thr = t; }
    }
    return thr;
}
```

#### (b) 切字 —— 这是整个方案最难的一步

中文/日文没有词间空格,字符常常**紧贴甚至粘连**,这是主要失败点。

三层递进策略:

**第 1 层:连通域标记(CCL)**

8 邻接的并查集扫描,得到每个独立笔画块。

```js
function connectedComponents(bin, W, H) {
    const labels = new Int32Array(W * H).fill(-1);
    const parent = [];
    const find = x => parent[x] === x ? x : (parent[x] = find(parent[x]));
    const union = (a, b) => { a = find(a); b = find(b); if (a !== b) parent[b] = a; };
    // ... 两遍扫描,第二遍用 union 合并等价标签
    return { labels, boxes };
}
```

**第 2 层:合并成字**

单个字可能被切成多块(如 `川`、`こ` 断笔),也可能多个字粘成一块。用启发式:

- 若两块 **x 投影重叠 > 60%** 且 **高度相近** → 认为是同一个字,合并
- 若一块 **宽度 > 1.6 × 行高** → 认为粘连,按行高做等分切割

**第 3 层:等宽兜底**

日文字幕绝大多数是**全角字符,宽度 = 行高**。所以当上面都失败时:

```
行高 H → 字符宽度 ≈ H → 从行首按固定步长切分
```

这个兜底在日文字幕上意外地可靠。

#### (c) 归一化

匹配能否成功,八成取决于归一化做得好不好。

```js
function normalize(gray, box, out = 32) {
    // 1. 裁到包围盒
    // 2. 等比缩放到 24×24（留边距），放进 32×32 画布
    // 3. 居中:按质心对齐,而不是按包围盒 —— 更抗抖动
    // 4. 灰度归一化到 0~1,再减去均值、除以标准差
    //    （这一步让匹配对整体亮度变化免疫）
    return vec;   // Float32Array(1024)
}
```

**减均值除标准差是关键**:它把"亮度"这个无关维度消掉,只留下形状。

#### (d) 匹配

用**归一化互相关**(NCC),等价于零均值归一化向量的点积:

```js
function ncc(a, b) {          // 两个已零均值归一化的向量
    let s = 0;
    for (let i = 0; i < a.length; i++) s += a[i] * b[i];
    return s;                  // 范围 -1 ~ 1
}
```

判决策略(双阈值):

| 最高分 | 动作 |
|---|---|
| ≥ 0.92 | 直接采用该标签 |
| 0.75 ~ 0.92 | 采用,但标记为"可疑",计入置信度 |
| < 0.75 | 视为新字符,建新模板 |

**性能优化:两级检索**

2000 个模板 × 1024 维 = 每字 200 万次乘加,一行 15 字就是 3000 万次。JS 大概 30~50ms,能接受但没必要。

优化:先用 **4×4=16 维的粗特征**筛出 top-20 候选,再用全维精算:

```
粗筛:2000 × 16  = 3.2 万次       → 拿到 top-20
精算:20 × 1024   = 2 万次        → 定最终结果
合计每字约 5 万次,比原来快 40 倍
```

#### (e) 标签获取 —— 别单字问,要整行问!

这是整个设计里最关键的技巧。

❌ **错误做法**:切出一个字,问模型"这是什么字"
→ 单字没有上下文,`わ`/`ね`/`れ`、`ロ`/`口`/`囗` 这类极容易认错

✅ **正确做法**:把**整行**发给视觉模型,让它读出整行文字
→ 有上下文,准确率天差地别

然后做**对齐**:

- 日文/中文是全角,基本 **1 字 = 1 字符**,按数量顺序对齐即可
- 若数量对不上(说明切字出错)→ 这一行**不学习**,只输出 API 结果,避免污染模板库

```js
// 对齐并学习
if (segments.length === line.length) {
    segments.forEach((seg, i) => lib.learn(seg.vec, line[i]));
} else {
    // 切字有问题,本行放弃学习
    Diag.record('切字数与识别字数不符', { seg: segments.length, text: line.length });
}
```

### 2.4 数据结构

```js
const TemplateLib = {
    items: [],           // [{ vec: Float32Array(1024), coarse: Float32Array(16),
                         //    label: 'あ', hits: 12, score: 0.95 }]
    byLabel: new Map(),  // label -> item,防止同一个字重复建模板

    learn(vec, label) {
        const existing = this.byLabel.get(label);
        if (existing) {
            // 同一个字多次见到 → 用滑动平均更新模板,越用越准
            for (let i = 0; i < vec.length; i++) {
                existing.vec[i] = existing.vec[i] * 0.8 + vec[i] * 0.2;
            }
            existing.hits++;
            return existing;
        }
        const item = { vec, coarse: coarse(vec), label, hits: 1 };
        this.items.push(item);
        this.byLabel.set(label, item);
        return item;
    },
};
```

**滑动平均更新**是个小亮点:同一个字见得越多,模板越接近该字体的"平均长相",抗噪能力越强。

### 2.5 成本模型

以一部 24 分钟动画为例(常见值,用于估算量级):

| 指标 | 数值 |
|---|---|
| 字幕行数 | 约 300~400 行 |
| 总字数 | 约 3000~4000 字 |
| **不重复字数** | **约 400~700 个** |

| 阶段 | API 调用 |
|---|---|
| 纯视觉引擎(现状) | 每行 1 次 → **约 350 次** |
| 模板自学习 | 每个新字所在行 1 次 → **约 80~150 次** |
| 学完之后 | **接近 0 次** |

**预计减少 70%~90% 的 API 调用**,而且速度从"等网络"变成"本地几十毫秒"。

### 2.6 风险(实话实说)

| 风险 | 严重度 | 缓解 |
|---|---|---|
| **切字失败**(粘连/断笔) | 🔴 高 | 三层递进策略;数量对不上就不学习 |
| 字体逐句变化 | 🟡 中 | 用 NCC 分数当门禁,失配就回落 API |
| 视频压缩噪点 | 🟡 中 | 归一化 + 滑动平均 + 双阈值 |
| 生僻字持续出现 | 🟢 低 | 学习期拉长而已,不影响正确性 |
| 模板库内存占用 | 🟢 低 | 2000 模板 × 1KB = 2MB |
| 跨视频污染 | 🟡 中 | 按 hostname 隔离,或干脆不持久化 |

**关于持久化**:建议**默认不持久化**。理由:

- 模板库是**字体相关**的,换一部片子字体就变了,存下来基本用不上
- 学习成本只有几十次 API 调用,重学很快
- 省掉 2MB 的 `GM_setValue` 读写和污染风险

如果要做,按 hostname + 字体指纹(行高 + 笔画宽度)哈希后存储,并设 1500 条上限。

### 2.7 实现规模

| 模块 | 预估行数 |
|---|---|
| 二值化 + Otsu | 60 |
| 连通域 + 切字(三层) | 180 |
| 归一化 | 70 |
| 模板库 + 匹配(两级检索) | 140 |
| 对齐 + 学习逻辑 | 80 |
| 管线接入 + 诊断 | 90 |

## 三、方案 B:PaddleOCR / ONNX

### 3.1 为什么值得考虑

**PaddleOCR 的中日文识别率明显高于 Tesseract**,尤其对**动漫描边字/艺术字**。这是它唯一的、但很硬的优点。

### 3.2 具体集成步骤

```
1. 加载 onnxruntime-web
   └─ ort.min.js + ort-wasm-simd-threaded.wasm（约 10MB）

2. 加载三个模型
   ├─ 检测  det:  PP-OCRv4/v5 det    约 4~5MB   （语言无关）
   ├─ 识别  rec:  japan_PP-OCRv4_rec 约 10~17MB
   └─ 字典  dict: japan_dict.txt      约 20KB

3. 自己实现后处理（难点）
   ├─ DB 后处理:阈值化 → 轮廓 → unclip 外扩 → 得到文本框
   └─ CTC 解码:  argmax → 去重 → 去 blank → 查字典

4. 流程: 图 → det → 裁剪文本框 → 缩放到 48×320 → rec → CTC → 文本
```

### 3.3 与油猴的冲突点(必须解决)

| 问题 | 说明 | 解法 |
|---|---|---|
| **ESM 模块** | ort 和模型加载库都是 ESM,不能直接 `<script>` 注入 | 用 `import()` 动态导入,或找 UMD 构建 |
| **跨域 Worker** | ort 要起 Worker,跨域脚本不能直接 new Worker | 拉取脚本 → `Blob` → `URL.createObjectURL` |
| **WASM 加载路径** | `ort.env.wasm.wasmPaths` 要指对 | 显式配置 CDN 前缀 |
| **CSP** | 和 Tesseract 一样会被拦 | `GM_addElement` |
| **多线程** | SIMD 多线程版需要 COOP/COEP 响应头 | 用单线程版,或放弃多线程 |

这几条加起来,复杂度不低。

### 3.4 CDN 与国内可用性

这是决定成败的一点:

| 来源 | 国内可用性 |
|---|---|
| `paddlejs.bj.bcebos.com`(百度自家 CDN) | ✅ **好** |
| ModelScope(RapidOCR 模型) | 🟡 一般 |
| jsdelivr / unpkg | ❌ 经常不通 |

**`@paddle-js-models/ocr` 走的是百度 CDN,这是它相对 ONNX 方案的最大优势。**

### 3.5 体积对比

| 项目 | 体积 |
|---|---|
| onnxruntime-web WASM | 约 10MB |
| 检测模型 | 4~5MB |
| 识别模型(日文) | 10~17MB |
| **合计** | **约 25~35MB** |

对比 Tesseract.js 的日文:几 MB 到几十 MB(取决于质量档)。
**体积上没有优势,优势纯粹在准确率。**

### 3.6 实现规模

| 模块 | 预估行数 |
|---|---|
| ort 加载 + 环境配置 | 120 |
| Worker / Blob 处理 | 100 |
| DB 后处理 | 200 |
| CTC 解码 | 120 |
| 图像预处理(归一化/缩放) | 130 |
| 模型管理与缓存 | 110 |
| **合计** | **约 780 行** |

## 五、建议

### 推荐:先做方案 C

理由:

1. **它是唯一能真正省钱的**。方案 B 只换识别引擎,API 调用一次不少 —— 而你真正持续付费的是 API
2. **零下载**,把你现在遇到的 CDN 问题从根上绕开
3. 和现有架构天然契合 —— 截图、区域、悬浮字幕、诊断都已经有了,只需要接一个新引擎
4. 失败了也不亏:识别不出来就回落 API,和现在行为一致

### 但要清楚它的软肋

**切字(CJK 字符分割)是成败关键。** 建议实现时:

- 先用**日文等宽假设**兜底(最简单,覆盖大多数情况)
- 再加连通域做增强
- **一定要实现"数量对不上就不学习"的保护**,否则错误模板会污染整个库

### 实施顺序建议

```
第 1 步  切字 + 归一化 + 可视化调试图
        └─ 先能稳定切出一行里的每个字，这是地基

第 2 步  模板库 + 匹配 + 自测（同一帧内自匹配应 100%）
        └─ 不接 API，先验证"同一个字能不能认出来"

第 3 步  接视觉 API 做整行标注 + 对齐学习
        └─ 验证学习曲线：API 调用是否真的快速下降

第 4 步  接入主管线 + 诊断面板显示命中率
        └─ 加"命中率 / API 节省数"指标，用数据说话
```

第 1 步做完就能判断可行性了 —— **如果切字不稳,后面全是空中楼阁**,那就退回 Tesseract 或上方案 B。

## 六、补充(v1.12.0):浏览器内置 AI 已经落地,本文的取舍需要重估

上面两个方案的共同前提是「本地 OCR 必须自己带模型权重」。v1.12.0 落地的
[`browser-ai` 引擎](../README.md#关于-browser-ai完全离线) 绕开了这个前提:
**模型由浏览器自己提供**(Chrome 138+ 的端侧模型),脚本一个字节都不下载,
也就不存在 CDN、体积、切字这些问题。

它提供两条识别路线,和本文两个方案正好形成替代关系:

| | 字符模板自学习(方案 C) | PaddleOCR / ONNX(方案 B) | **浏览器内置多模态读图**(已实现) |
|---|---|---|---|
| 额外下载 | 0 | 25~35 MB | **0**(模型由 Chrome 提供,首次由用户点按钮触发下载) |
| 需要自己实现 | 切字 + 模板库 + 对齐(约 620 行) | 模型加载 + WASM 集成(约 780 行) | **无**(调 `LanguageModel` 即可) |
| 中日文准确率 | 取决于视觉模型与切字 | 最好 | 一般(明显不如 PaddleOCR) |
| 前提 | 字体字号全片一致 | 能下到模型 | Chrome 138+ 桌面版、HTTPS/localhost、非跨域 iframe |

**结论**:方案 B / C 想解决的问题(不联网、不花钱)已经有了成本低得多的答案,
所以两者都不建议再实现。真要追求离线识别率,推荐直接用**本机 Umi-OCR**
(见 [`44-umi-ocr.js`](../src/44-umi-ocr.js)),它识别率最高、浏览器端同样零下载;
`browser-ai` 的「内置多模态读图」只适合「连 Umi-OCR 都不想装」的场景。
